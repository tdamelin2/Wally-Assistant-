Implementation decisions resolving the findings:
- Preserve the precise transition matrix: fresh eligible phone turn -> PHONE_PENDING until now+180000; same-id phone=true with >=60000ms left -> same turn/deadline/fresh prompt; same-id false or <60000ms left -> atomically RUNNING, direct HP once; same-id after final -> stored reply. An expired result finishes interrupted and returns409; duplicate/final/no row result409; wrong chat/deleted chat404; mismatched r:messageId400. A different message gets busy503 until expiry, then the old turn closes and the new one proceeds. A no-write HP timeout deletes only its reply row and returns503; any effect/requested-tool fence prevents another rung from repeating work.
- Use the same finalization for phone/HP/code outcomes: mint chip tokens, preserve pending action/dream/action/card receipts, set final brain, finish assistant and user request states. Phone results derive permission/text from the stored user. Claim before validator; recheck active chat/user/reply at the claim and protect closure/eviction/summary against an orphan effect. Deleted/archived turns never become recreated replies.
- Start expiry independently of seedStore configuration/failure, after chatService construction. An expiry scan must not wait behind a long already-claimed RUNNING HP request and delay other pending chats. Re-read state after the per-chat lock; never let tick overwrite a claimed/finished response.
- Foreground loss cancels the phone job, clears provisional UI and retains its outbox item for expiry/reconciliation. Defer Android background outbox delivery when it could claim an abandoned phone turn; simplest bounded policy is foreground-only Android chat draining while background sync/reminders still work. Resume drain on foreground entry. Keep desktop drain behavior. Do not treat lifecycle cancellation as null/timeout and trigger HP immediately. Recheck switch/file/battery/power/foreground after202 and after waiting for native slot. Settings Test follows the same eligibility default pending Q03.
- Keep one engine warm, create/close a fresh conversation for each generate. All settings/chat/eval requests share that owner. GPU init failure cleans up before CPU attempt; report actual backend. Cancellation invokes the pinned native cancellation mechanism and waits for a terminal callback/quiescence before handles close or the slot is reused. Idle/trim unload goes through the owner with generation checks. Official [API overview](https://developers.google.com/edge/litert-lm/api_overview) and [constrained-output issue](https://github.com/google-ai-edge/LiteRT-LM/issues/1662) support the approach; [upstream Conversation source](https://github.com/google-ai-edge/LiteRT-LM/blob/main/kotlin/java/com/google/ai/edge/litertlm/Conversation.kt#L475) exposes the cancellation risk but is not proof of0.19.1 behavior.
- PHONE context is a separate profile: next seven Jerusalem days' events/exams,12open tasks,today's meals/spending values,Sunday-to-today spending total,existing dream-gated source. Allocate the3000char budget so totals do not disappear behind long names; preserve HP1200 output. Actual prompt length includes voice/instructions/history/notes/question/schema overhead, so real smoke/eval must validate production packs after the Gallery free-text gate.
- Streaming lexer only recognizes top-level answer kind/reply; escape/surrogate/field-order/nested-string cases are tested. Bind every partial/probe/finally update to its operation and current-chat projection. Only final server DTOs carry cards/chips/Undo. Follow stream growth at the bottom without forcing a user who scrolled upward back down.
